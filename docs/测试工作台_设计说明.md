# 测试工作台设计说明

> 本文档沉淀测试工作台的产品价值、数据设计、流程说明、已定稿决策与实现对齐记录。
> 功能需求、验收规则和约束以 [测试工作台_产品说明.md](测试工作台_产品说明.md) 为准。

---

## 1. 产品定位与范围

测试工作台是以项目为边界的 AI 测试资产工作台。它把一次完整的测试过程——需求澄清、用例设计、执行记录、缺陷处理、遗留跟踪——沉淀在同一条可追溯的链路上，并在需求与用例环节引入 AI 辅助，帮助团队更快、更全地完成测试。资产以系统与版本为边界组织，一个版本内走完完整的测试闭环。

设计取向：轻量、够用、闭环。只做团队真实需要的核心流程，不做过重的能力。

核心主张：

- **轻量闭环**：需求 → 用例 → 执行 → Bug → 遗留，一条链路走完，不堆砌复杂功能。
- **AI 用在刀刃上**：AI 只用在最费人力的少数环节——把需求问完整（对原始需求进行追问+补全）、单系统+版本内进行需求合并、对已确认需求通过生成对话澄清后生成测试用例。
- **版本是交付单元**：资产按系统 / 版本组织，工作时聚焦当前系统与版本；当前系统的同一个版本内的需求、用例、执行、Bug、遗留形成一条可回顾的完整链路。

---

## 2. 平台价值

测试工作台要解决团队测试过程中两处真实痛点：**需求含糊导致用例漏测、测试资产散落在文档和聊天记录里无法追溯**。它将完整测试过程组织为可回顾的链路，并只在最费人力的环节引入 AI，让“想清楚”和“测下去”都更省力。

- **把需求问清楚，从源头减少漏测**：通过 AI 追问，把口头默认的边界、异常和冲突明确下来，再整理为完整正文与结构化内容，提升下游用例覆盖质量。
- **AI 用在刀刃上，人只做判断**：AI 承担追问、整理、合并、结构化和用例生成；预览、确认、执行、验证均由人工把关，避免静默写入。
- **一条链路全程可追溯，资产沉淀而非散落**：需求、用例、执行、Bug、遗留项按项目、系统和版本组织，保留必要的来源关联。
- **以交付范围组织，轻量而闭环**：资产按项目、系统、版本三级作用域组织，日常聚焦当前系统与版本；数据看板展示资产数量与待处理事项，复用平台统一的权限能力。

一句话概括：**用 AI 把需求问完整、把零散资产合起来，用一条可追溯的轻量链路让测试从想清楚到测闭环。**

## 3. 数据模型

核心业务资产在项目、系统、版本三级作用域下组织，并带软删除与审计字段；AI 消息、执行流水与 Bug 流转记录的审计字段以第 8 节各表定义为准。

| 实体 | 关键内容 |
| --- | --- |
| 项目 | 名称、描述、标签、主题色、是否公开 |
| 系统 | 所属项目、系统名称、系统类型、描述 |
| 版本 | 所属项目、所属系统、版本号、描述、计划发布日期、实际发布日期、当前阶段 |
| 原始需求 | 所属项目、所属系统、所属版本、需求编号、需求标题、来源、原始需求内容、需求内容、状态（待确认/已确认） |
| 合并需求 | 所属项目、所属系统、所属版本、需求编号、需求标题、需求内容、来源需求、合并状态 |
| 测试用例 | 所属项目、所属系统、所属版本、用例编号、用例标题、关联原始/补全/合并需求、前置条件、操作步骤、优先级、预期结果、确认状态、执行状态（由执行派生）、来源（AI 生成/人工创建） |
| 测试执行 | 测试用例、结果（通过/失败/未执行）、实际结果、备注、执行人、执行时间（流水式追加，用例执行状态取最近一次） |
| Bug | 所属项目、所属系统、所属版本、Bug 标题、关联需求、关联用例、复现步骤、实际结果、预期结果、严重级别、优先级、状态、指派处理人、解决方案说明、验证结论、流转记录 |
| 遗留项 | 所属项目、所属系统、所属版本、计划处理版本、关联需求、关联用例、关联 Bug、遗留项标题、类型、描述、优先级、状态 |

关系要点：需求是中心节点，结构、用例、Bug、遗留项均可关联到需求；需求合并在同一系统同一版本内进行，产出完整需求。版本号仅在当前项目的同一系统内与未软删除版本比较唯一，不同项目或不同系统允许重复。项目复制仅包含未软删除的系统、版本和原始需求，重建系统、版本和原始需求关联与编号；不复制 AI 补全需求、AI 合并需求、测试用例、Bug、执行记录、遗留项和审计日志。

## 4. 已定稿决策

- **需求状态**：收敛为“待确认 / 已确认”两态；原始需求、AI 补全需求和 AI 合并需求保存后均为待确认，由用户通过确认操作置为已确认；仅编辑 Markdown 正文时才回退为待确认；状态不开放自由下拉。
- **AI 用例保存方式**：生成结果由人工勾选确认后保存；保存后在待确认列表内编辑，生成弹窗不承担大量编辑操作。
- **追问维度与交互**：补全、合并与用例生成对话共用“必须确认 / 冲突 / 遗漏 / 建议”四组骨架和同一套 AI 对话交互。三者首轮均先完成全面审查并尽可能一次问全：按适用功能点检查流程、角色、触发条件、操作、数据、状态、反馈、异常边界、关联影响、验收和测试覆盖。问题是否提出以答案会不会改变需求正文、测试范围、数据、步骤、预期、正反向或边界覆盖为准，不以是否完全阻塞开发为门槛。AI 合并按“去重、冲突识别与已确认取舍、首轮集中追问、完整正文、人工预览确认”执行；跳过的问题不阻塞保存，但后续正文和用例不能把未确认内容编造成规则或确定性预期。用例生成对话等同于“从测试设计视角澄清需求”，但不保存独立测试点资产；首轮注入完整的**系统预置、文件驱动的测试维度关键词清单**（`backend/docs/prompt/requirement_keywords.md`），后续不重复注入完整清单，只携带覆盖结果、未覆盖维度及因用户补充触发的相关关键词子集。
- **追问收敛机制**：首轮不刻意压少问题数量（仅设 50 条总量安全上限），一次性问全问透；来源已有直接结论、唯一业务语义及未声明的实现细节不追问，也不为凑数量发散。**补全与合并的首轮均必须输出一组问题、四组不得同时为空、暂不限制数量**——即使需求已相当完整，也至少给出一组确认型问题（如「无需再补充/调整」）保持未收敛，交由用户点选后再收敛，从源头避免首轮零问题时对话无处可点。后续轮只处理本轮回答真正引出的新边界、冲突或测试覆盖差异。各流程均靠禁止重复、相似度去重和垃圾过滤防止重复；普通补全最多 5 轮，AI 合并最多 3 轮。合并的关键冲突必须回答或明确跳过后才能整理；跳过时正文保留双方规则及适用条件。
- **需求合并粒度**：采用**对话式合并流程**（选择来源已确认需求 → 直接进入合并对话并可选填标题 → 确认冲突、补全合并后缺口 → 按业务顺序整理为合并正文 → 预览并保存），当前仅支持同一系统、同一版本内合并；跨版本合并能力后续可扩展。合并始终保留用户选择的来源类型；选择 AI 补全需求时，重新合并仍读取补全正文，不覆盖或降级补全资产。
- **直接生成用例**：一次只选择一种已确认需求类型，可选择同类型多条需求。生成前 AI 首轮以测试设计视角补全会改变测试范围、测试点、步骤、测试数据或预期结果的信息；用户回答、跳过或补充后，必须经过服务端收敛门禁，至少存在一轮有效回答/跳过/补充，且阻塞问题全部已回答或跳过，才能开始生成。生成过程保留在同一 AI 对话内，成功后由助手气泡提供「查看并保存测试用例」入口，点击后再打开预览勾选保存。多来源逐条独立生成时单条失败不影响其余：失败来源单独记录并跳过、成功结果照常返回，仅全部失败才整体报错，并回传失败来源与疑似被截断来源清单供前端提示。生成用例逐项覆盖明确功能点及确认结论，不保存分析正文或其他中间资产。未确认、跳过或来源未涉及的内容不得编造成业务规则；无法可靠对应的细粒度引用保持为空。
- **对话输入与补充**：常规作答只在问题卡片内完成（选择题勾选、开放题在题内文本框作答）。AI 本轮无新问题时，仅在最新 AI 回复内提供紧凑的补充输入；提交后作为已知事实与原文、历史问答做语义去重，已明确的信息不重复追问，仅追问新增边界、冲突或未覆盖的测试差异。只要返回待确认题，导语和顶部状态统一提示继续作答，不显示已完成或整理引导；不提供全局底部输入框。
- **对话输入与提示词展示**：每条“我的输入”完整保留并默认收起，用户内容按纯文本展示；每轮同时展示实际使用的模型、调用分组、结构化选择、自定义输入、跳过状态和补充原文，支持复制，不能只展示摘要或最终答案。追问提示词、补全关键词和整理提示词以独立 Markdown 区块展示，默认收起，可单独复制，整条输入复制为 Markdown。首轮展示完整关键词清单，后续展示覆盖摘要、未覆盖维度和实际使用的相关关键词子集。提示词随每轮实际调用一并展示，整理成文展示对应整理提示词；追问统一约束输入、业务边界、去重、轮次与结构化输出，整理正文以内容守恒和已确认结论落位为准。
- **结果对比核对**：最终整理结果气泡同时提供“预览并保存”和“预览并对比”。后者先二次确认，再在原对话中追加一轮只读 AI 核对，复用用户输入/提示词/思考/输出/复制交互；核对输入包含来源正文、已确认问答和补充内容、最终 Markdown，禁止重写正文。完成后打开只读对比弹窗：前后对比以原文与 Markdown 预览双栏展示，纳入概要按已纳入、部分纳入、未纳入、已跳过归类并给出正文依据。概要不随资产保存，避免人工后续编辑后失真。
- **失败重试**：追问或整理调用失败时保留失败气泡并提供统一模型选择组件。候选必须满足可见、已启用、未失效、正额度且仍有剩余；首次返回的候选可排除失败模型，重试弹窗打开或刷新时重新获取最新可用模型，若失败模型额度恢复则允许再次选择。平台模型额度用尽时可展示可用的我的模型，用户明确选择并确认后才发起新调用。网络、超时或服务异常时也不得自动重试或自动切换模型。**仅当确有其它可切换候选模型时**，才锁住提交回答、继续补充和结束整理、要求先选择模型并确认重试，成功后恢复继续调用；**没有任何候选模型时不锁死对话**（只提示检查模型配置和额度，并提供刷新可用模型入口），用户仍可基于已确认内容正常结束或刷新后再试，避免只有一个模型或额度用尽时整段对话卡死。失败气泡须保留上游真实原因：上游以 HTTP 报错或以 200 响应但流内嵌错误体（如 `{"error":{"message":...}}`）两种情形，最外层兜底都要透传已提取到的可读消息，仅在异常无任何可读文案时才退回技术类名，不得用类名覆盖已有原因。
- **合并来源展示**：合并对话在用户输入气泡中以编号与标题组成紧凑来源清单，不叠加关键词；每条来源正文默认收起，支持单条复制/展开，以及多来源下的全部展开、全部收起。合并正文不写入来源需求编号，详情来源列表负责追溯。
- **思考、计时与停止入口**：思考中默认展开；收到首段正式输出后自动收起一次，后续推理增量、输出和题组整理均不再改变展开状态，用户可手动展开。生成期间助手气泡右上角显示前端实时走秒；停止入口位于对话滚动区下方的独立右侧操作栏，使用带呼吸光晕的圆形停止图标，悬停提示“停止生成”，点击后须二次确认，非生成态隐藏。
- **修订能力**：不维护面向用户的独立修订链，采用内容就地更新与操作日志留痕。
- **Bug 指派时机**：允许先提交后指派。
- **项目内权限**：超管、管理员和项目创建人可维护项目内全部资产；进入公开项目的普通用户可查看全部资产并创建新资产，但只能编辑、删除和常规流转自己创建的资产。AI 补全、AI 合并、AI 生成用例可读取当前项目可见来源，不受来源创建人限制，产物归操作人。
- **项目删除与数据清理**：项目删除沿用项目级管理权限，确认后在同一业务操作中级联软删除项目及其系统、版本、需求、用例、Bug、遗留项、执行记录和 Bug 流转记录，不要求预先删除项目内资产；审计日志保留。看板“清空项目数据”是独立的部分数据清理能力，不删除项目本身。
- **批量删除权限与一致性**：选中记录先统一做权限预检，存在无权限记录时整批不执行；“全部删除”由后端按当前用户可维护范围执行，普通用户只处理自己创建的记录并返回跳过数量，业务删除在单事务中提交。
- **Bug 流程责任**：新建 Bug 不展示验证人，后端固定以创建人作为默认验证人；被指派处理人可执行解决动作，验证人可执行验证动作，二者均不因此获得常规编辑、删除权限。
- **Bug 弱关联**：Bug 可独立创建，也可关联需求、用例和执行流水。通过用例提交 Bug 时优先追溯用例已有的原始需求；没有可用原始需求时关联需求保持为空，不因追溯失败阻断提单。

仍需团队持续关注：追问轮的输出预算需要结合思考型模型表现确定，必要时限制思考输出，避免消耗预算后返回空内容。

## 5. 核心流程

```text
① 建项目 → 建系统 → 建版本
        │
        ▼
② 新建需求（仅需标题；正文可选）
        │
        ├─ 手动编辑需求正文（Markdown）→ 点“确认”→ 已确认
        └─ AI 补全（三段）：① 追问（必须确认/冲突/遗漏/建议，AI 只提问不写正文）
                    → ② AI 整理成文（调 AI，把本次对话收敛成需求正文，可随时预览/手动编辑/停止生成）
                    → ③ 预览并保存（瞬时、不调 AI，校验正文非空）→ 新增已落库、待确认的 AI 补全需求并在保存时分配编号 → 用户确认后成为正式来源
        │
        ▼
③ （需要时）同系统同版本内多条零散已确认需求 → AI 合并（对话式追问，复用补全对话组件）→ 结束对话并整理成合并正文 → 预览并保存（落库为待确认、在保存时分配 MREQ 编号）→ 用户确认后成为正式来源
        │
        ▼
④ 已确认原始/补全/合并需求 → AI 用例生成对话（必要时一次性追问）→ 服务端收敛校验 → 直接生成用例预览（勾选确认保存）/ 手工补充用例 → 批量确认
        │
        ▼
⑤ 执行用例（已确认用例，轻量流水式）：通过 / 失败 / 未执行
        │              └─ 单用例失败时默认可提交已关联执行流水的 Bug
        ▼
⑥ Bug 闭环：测试提交 → 开发解决 → 测试验证（通过关闭 / 不通过重激活）
        │
        ├─ 转为遗留项 → 创建关联遗留项，原 Bug 保留流转记录并标记为遗留
        ▼
⑦ 数据看板全程可见（按所选作用域）：各类资产数量、未关闭 Bug 数、待处理遗留数
```

| 需求追问 | 必须确认、冲突待确认、遗漏场景、建议补充、连续编号、已确认事实；首轮注入完整预置维度关键词，后续携带覆盖/未覆盖摘要和相关关键词子集 | [requirement_refinement.md](../backend/docs/prompt/requirement_refinement.md)、预置词 [requirement_keywords.md](../backend/docs/prompt/requirement_keywords.md) |

## 7. 实现对齐记录

以下为当前实现已经落地的关键对齐项，作为设计与代码的同步索引。

- **AI 合并需求详情交互**：列表移除“查看”，保留“编辑”，需求标题点击直接打开编辑弹窗；详情 tab 固定为“合并预览 → 来源需求”，合并预览展示自身编号，来源需求列表展示来源编号与标题，不展示版本指针和历史结构化记录，并对状态/来源数量标签增加间距。
- **AI 用量消费口径**：调用结果只分成功、失败，且与已用独立判断：模型内容通过业务解析和结构校验才记成功并计 1 次；其余未得到可用结果均记失败。已收到内容但输出过短、解析或结构校验失败计 1 次；执行前明确拒绝且未返回内容不计消费；已发起后超时、网络中断等无法确认结果计 1 次。历史空结果查询时按失败展示，不改写数据。调用记录结果筛选由后端执行。今日与按天选择当天统一按北京时间自然日查询，超级管理员平台额度无限制。

- **需求查看弹窗关联用例的执行状态“未测”中文映射**（已处理）：已补充中文映射，不再直接显示英文枚举值。

## 8. 库表结构

以下内容以当前 SQLAlchemy 模型定义为准。测试工作台自身包含 11 张业务表；`users` 为平台公共用户表，仅被外键引用，不在此重复定义。

### 8.1 通用字段

除特别说明外，业务主表均包含以下字段；各表小节会明确采用的通用字段组合。所有测试工作台表和字段均维护中文数据库注释，初始化程序会幂等同步注释；历史遗留表及其关联列在初始化迁移中按“解除外键 → 删除列 → 删除表”的顺序安全清理。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | `INT`，主键 | 记录唯一标识，建立索引。 |
| `is_deleted` | `BOOLEAN`，默认 `false` | 软删除标记；业务查询默认排除已删除数据。 |
| `deleted_at` | `DATETIME`，可空 | 软删除发生的时间。 |
| `created_by` | `INT`，外键 `users.id`，可空 | 创建人的用户标识。 |
| `updated_by` | `INT`，外键 `users.id`，可空 | 最后更新人的用户标识。 |
| `created_at` | 带时区 `DATETIME` | 创建时间，使用北京时间默认值。 |
| `updated_at` | 带时区 `DATETIME` | 最后更新时间，更新记录时自动刷新。 |

### 8.14 列表筛选与用例确认

- 系统、版本、原始/补全/合并需求、用例、Bug、遗留项共用项目资产分页查询；前端仅传递已提交的筛选条件，后端负责项目范围、筛选、排序与分页。左下角范围只在当前项目内生效。
- 用例以 `draft`（待确认）和 `confirmed`（已确认）分页展示。待确认可确认，已确认可执行或批量取消确认；取消确认仅允许处理当前作用域内的已确认用例，退回 `draft` 时不删除历史执行记录。
- 单用例执行使用专用执行弹窗，保存执行流水时可携带实际结果和备注；新建失败记录默认选择提交 Bug，先保存执行流水再打开带入用例、执行、实际结果和预期结果的 Bug 表单。批量执行只记录所选已确认用例的同一结果，不触发逐条建 Bug。
- 全部页签的批量确认和批量取消确认按所选记录的确认状态分别处理；后端再次校验项目、系统、版本及状态，避免跨范围或重复状态变更。
- Bug 指派候选人使用项目内专用接口，只返回启用用户的编号和显示名称；不复用仅超管可访问的用户管理接口。

## 8.1 用例生成调整

- `test_case` 对话仍复用追问状态机和内部轮次兜底，但前端统一称为“生成规则”，首轮保留任务说明、规则和来源快照。
- 来源需求查询使用项目级分页接口，按来源类型、当前项目系统范围、当前项目版本范围和编号/标题关键字筛选；仅返回已确认且未失效的需求。列表返回需求标题、所属系统、所属版本、创建时间及创建人姓名（连接用户表取真实姓名、无则取昵称）用于展示，不单独展示需求编号但仍支持按编号搜索。前端维护跨页已选清单，不再预加载全部需求。
- 生成范围不再要求同一系统、同一版本：后端校验每条来源属于当前项目且落在传入的系统、版本筛选范围内；模型仍按来源逐条调用，输出保留来源、系统和版本关联，不推断跨系统流程。
- 项目范围选择器采用“系统 / 版本”两个联动 Tab。系统多选后版本 Tab 启用并按已选系统过滤，取消系统时清理其下版本；全部范围使用显式标记，查询和分页均由后端执行。
- 模型信息同时提供追问规则与正式生成规则预览；开始生成时把正式生成提示词作为可折叠、可复制区块写入用户消息，并以接口实际读取的提示词回填。
- 结算作答时，把答案草稿快照保存到对应助手问题消息；只读问题卡据此高亮已选项，并显示自定义输入或跳过状态。
- 生成接口返回类型、优先级分布和质量提示；前端不为 AI 缺失的优先级补默认 P2，而是显示“待补充”并阻止保存。保存接口（单条新建与批量保存）在服务端再次校验优先级必须为 P0/P1/P2/P3，缺失或非法即按业务错误拒绝、不静默补默认值，作为绕过前端时的最终依据。
