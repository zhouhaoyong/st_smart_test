# 测试工作台产品说明

## 1. 这套功能解决什么问题

测试工作台用于把需求、测试用例、缺陷和测试进度放在同一个业务链路中管理。

它帮助团队完成：

- 按项目、系统和版本管理测试范围；
- 把需求拆成可验证的测试内容；
- 编写、评审、执行和维护测试用例；
- 记录缺陷、跟踪处理过程和验证结果；
- 查看项目质量进展；
- 处理待办事项；
- 使用 AI 辅助补全需求和生成测试用例。

这份说明面向产品使用者，重点解释真实业务中的使用方式。页面实现约定见 [测试工作台设计说明](./测试工作台_设计说明.md)。

## 2. 谁可以使用

| 使用者 | 主要职责 |
| --- | --- |
| 项目负责人 | 维护项目范围、组织测试并关注整体进度 |
| 测试人员 | 分析需求、编写和执行用例、提交及验证缺陷 |
| 开发人员 | 查看用例和缺陷，处理开发中的问题 |
| 产品人员 | 提供需求、确认业务规则并参与验收 |
| 管理人员 | 查看项目质量和权限范围内的统计信息 |

具体能否新增、修改、删除、执行或关闭某项内容，以项目权限为准。页面看得到，不代表一定有修改权限。

## 3. 使用前需要理解的几个概念

| 概念 | 说明 |
| --- | --- |
| 项目 | 一项业务或产品工作的总范围 |
| 系统 | 项目中的具体业务系统或产品模块 |
| 版本 | 系统某一次发布或测试范围 |
| 需求 | 需要验证的业务目标、规则或功能 |
| 测试用例 | 用于验证需求是否满足的一组步骤、数据和预期结果 |
| 缺陷 | 实际结果与预期不一致，需要跟踪处理的问题 |
| 遗留项 | 暂时保留、尚未纳入当前版本正式测试的事项 |
| 仪表盘 | 从整体上查看测试数量、执行状态和质量情况 |
| 待办 | 需要当前用户继续处理的事项 |

一条完整的业务链路通常是：

确定项目和版本 → 整理需求 → 生成或编写测试用例 → 执行测试 → 提交缺陷 → 修复后验证 → 查看项目质量。

## 4. 第一次使用怎么开始

1. 进入项目，选择要工作的系统和版本；
2. 确认当前版本的需求是否完整；
3. 对需求进行拆分，补充测试范围和验收条件；
4. 编写测试用例，或使用 AI 先生成草稿；
5. 评审并确认用例；
6. 执行用例，记录通过、失败或未执行；
7. 对失败结果提交缺陷，修复后重新验证；
8. 在仪表盘或待办中查看项目进展。

如果只是查看历史内容，应先切换到对应系统和版本，避免在当前版本中误修改或误执行。

## 5. 项目与测试范围

### 5.1 项目范围

项目是工作台的最外层范围。一个项目可以包含多个系统，每个系统又可以有多个版本。

### 5.2 系统和版本选择

页面上方的范围选择器决定当前正在查看和操作的内容。选择后，需求、用例和缺陷等内容会按当前范围过滤。

系统和版本的使用规则：

- 新进入项目时，默认进入系统和版本的当前推荐范围；
- 用户最近选择的范围会被记住，方便继续工作；
- “全部”适合查看汇总，不适合直接批量修改；
- 切换范围后，新增内容会归入当前选中的系统和版本；
- 仪表盘和待办是跨范围查看的入口，系统和版本管理本身不受普通内容筛选影响。

操作前先确认当前范围，是避免把需求或用例加错版本的关键步骤。

### 5.3 项目删除

项目删除是项目级操作，只对项目创建人和超级管理员开放，并需要二次确认。确认后，项目及其下的系统、版本、需求、测试用例、Bug、遗留项和执行记录会统一软删除，不需要先逐项删除项目内数据；历史审计日志保留。若只是想清理部分业务数据，应使用数据看板中的“清空项目数据”，不要删除项目。

## 6. 系统和版本管理

系统用于区分不同业务模块，版本用于区分不同发布或测试批次。

常见操作包括：

- 新增、编辑和删除系统；
- 新增、编辑和删除版本，并填写版本说明、当前阶段和发布日期；
- 查看当前版本包含的需求、用例和缺陷。

删除采用软删除，历史数据不会直接从数据库中清除；需要测试新的范围时，应创建或选择新的版本。

## 7. 需求管理

### 7.1 需求从哪里来

需求可以手动录入，也可以导入已有资料。录入时应至少说明：

- 业务要解决什么问题；
- 谁会使用；
- 在什么条件下触发；
- 预期结果是什么；
- 哪些情况不在本次范围内。

需求描述越接近真实业务，后续生成用例和评审越准确。

### 7.2 需求的三种查看方式

需求页面通常提供三类内容：

- 待处理：刚录入、还需要补充或确认的需求；
- 已确认：已经经过人工确认，可以进入测试设计；
- 全部：按当前系统和版本查看完整需求。

AI 补全、人工补充和合并结果是不同阶段。AI 给出的内容先作为建议，人工确认后才算正式需求。

### 7.3 AI 补全需求

当需求只有标题、简要描述或零散资料时，可以使用 AI 辅助补全。

使用流程：

1. 选择需要补全的需求；
2. 补充业务背景或回答页面提出的问题；
3. 查看 AI 整理出的内容；
4. 修改不准确或不符合项目实际的部分；
5. 确认后保存。

如果某个问题暂时无法回答，可以跳过并继续。跳过不等于系统认为该条件不存在，后续仍应在评审时补齐。

AI 不会替用户确认需求，也不会在用户未确认时覆盖原内容。

### 7.4 合并需求

当多个需求描述的是同一个业务目标，可以在同一系统和版本中合并。合并前应确认：

- 是否真的属于同一个业务目标；
- 是否会丢失不同角色、不同条件或不同验收要求；
- 合并后的标题和描述是否能让测试人员直接理解。

合并完成后，原需求的关联关系应能追溯，避免后续无法解释来源。

## 8. 测试用例管理

### 8.1 用例应该写清楚什么

一个可执行的测试用例至少要让另一个人看懂：

- 测试目的；
- 前置条件；
- 操作步骤；
- 输入数据；
- 每一步的预期结果；
- 整体通过标准；
- 优先级或重要程度。

涉及权限、异常、边界值和数据变化时，应分别写出对应场景，不要只写一个笼统的“验证功能正常”。

### 8.2 用例的来源

用例可以：

- 手动新建；
- 根据已确认的需求由 AI 生成初稿；
- 在已有用例上继续编辑和补充；

AI 生成的是可编辑草稿。保存前要检查需求对应关系、步骤、数据和预期结果，确认后再进入正式用例列表。

### 8.3 用例状态和操作

用例一般会经历：

草稿或待确认 → 已确认 → 记录执行结果 → 根据结果继续维护。

页面中的筛选用于区分待处理、已确认和全部用例。执行后应保留最近结果和历史记录，便于判断是首次失败还是回归失败。

用例发生业务变化时，不建议只修改标题。应同步检查前置条件、步骤、数据、预期结果和关联需求。

### 8.4 执行用例

执行前确认：

- 当前系统和版本；
- 使用的数据；
- 前置条件是否满足；
- 用例是否已经确认；
- 执行结果需要记录给谁。

执行结果可以是通过、失败或未执行。失败通常表示实际结果不符合预期；未执行表示本次没有形成有效执行结论，例如环境、依赖服务或测试数据尚未准备好，具体原因可记录在执行备注中。

## 9. 缺陷管理

### 9.1 什么时候提交缺陷

当实际结果与用例预期不一致，并且排除环境、数据和操作错误后，应提交缺陷。

缺陷描述至少包含：

- 问题发生的系统和版本；
- 复现前提；
- 具体操作步骤；
- 实际结果；
- 期望结果；
- 影响范围和紧急程度；
- 相关截图、日志或测试数据（如有）。

一个好的缺陷描述应让开发人员能够复现问题，而不是只写“功能不对”。

### 9.2 缺陷处理过程

缺陷通常经历：

待处理 → 处理中 → 待验证 → 已解决或关闭。

如果验证仍然失败，应退回处理并补充新的实际结果。关闭缺陷前，应确认修复内容、影响范围和相关用例都已经验证。

缺陷的状态流转和处理记录应保留，便于追踪谁在什么时候做了什么决定。

### 9.3 缺陷与用例的关系

缺陷最好关联发现它的测试用例和需求。这样可以回答：

- 哪条需求受影响；
- 哪个场景未通过；
- 修复后需要回归哪些内容；
- 同类问题是否重复出现。

## 10. 遗留项

遗留项用于记录暂时不能纳入当前版本正式测试，但又不能遗忘的内容，例如：

- 已知但暂不修复的问题；
- 等待外部条件的需求；
- 后续版本再处理的测试场景；
- 暂时无法验证的风险。

遗留项应写清原因、责任人、后续处理时间或重新评估条件。它不是“删除”，也不代表当前问题已经解决。

## 11. 仪表盘与待办

### 11.1 仪表盘

仪表盘用于快速了解项目质量，不替代具体的需求、用例和缺陷明细。

通常关注：

- 当前版本需求和用例的数量；
- 已确认、待处理和执行结果的进度；
- 通过、失败和未执行情况；
- 缺陷的严重程度和处理状态；
- 哪些模块或版本风险较高。

看到异常数字时，应回到明细确认原因，不要只根据统计结果下结论。

### 11.2 待办

待办集中展示当前用户需要继续处理的事项，例如待确认需求、待评审用例、待验证缺陷或待补充信息。

处理待办后，应回到原业务内容完成确认或填写结果。仅打开待办不代表事项已经完成。

## 12. AI 能力的使用边界

工作台中的 AI 主要用于两类工作：

- 把不完整的需求整理成更容易评审的业务描述；
- 根据需求生成测试用例初稿。

使用 AI 时请遵守：

- 先选择合适的模型，再开始生成；
- 生成结果先预览，人工检查后再保存；
- 业务规则、权限和验收标准必须由业务人员确认；
- AI 不会自动执行测试，也不会静默修改正式内容；
- 模型失败时，由用户选择其他可用模型后重试；
- 涉及敏感业务资料时，先确认组织的数据使用规则。

## 13. 权限与安全

- 项目权限决定能否查看或修改内容；
- 需求、用例、缺陷的处理权限可以不同；
- 开发人员通常需要查看和处理缺陷，但不一定能修改测试范围；
- 测试人员可以维护测试内容，但不一定能管理项目成员；
- 关闭、删除或批量变更等操作应谨慎确认；
- 不要在需求、缺陷或附件中暴露不必要的密码、令牌和个人信息。

## 14. 当前使用边界

- 工作台负责管理测试业务过程，不替代接口测试、性能测试或线上监控系统；
- 执行结果依赖被测系统、测试数据和环境状态；
- AI 生成内容不能直接视为最终需求或最终用例；
- 复杂跨系统流程需要根据项目实际拆分和协作，不应只依赖一条用例描述；
- 历史数据用于追踪和复盘，不能因为切换版本就当作当前版本结果。

## 15. 页面使用约定

- 查询条件需要点击查询按钮后才生效；
- 列表数据较多时使用分页，默认每页 10 条；
- 当前系统和版本会显示在页面范围选择器中，新增内容前请再次确认；
- 长文本在详情中完整查看，页面主体保持在内容区域内滚动；
- 删除和可能影响历史记录的操作需要再次确认；
- 时间统一按北京时间展示，提示信息以服务端返回内容为准。
